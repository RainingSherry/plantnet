# CS 一区选题 + 承上启下毕业论文 —— 战略思路（2026-07-03）

配套文献表：`文献汇总.csv`（48 篇，按 A-H 分类）。

## 0. 你的两个诉求，和一个必须先接受的现实

诉求：(1) 一篇 **CS 一区**（CCF-A：NeurIPS/ICML/ICLR/KDD/… 或 CCF-A 期刊）方法论文；
(2) 论文**承上启下**，毕业论文能顺着展开——做一个**把单细胞降维/聚类/上下游算法迁移到
GPU 的 Agent**。

必须先接受的现实（残酷但重要）：

```
纯"植物上更好的聚类方法" → 最高只能进生信一区(Bioinformatics/Genome Biology/
                          Nature Methods)，进不了 CS 一区。
```

证据：查遍 2025-26，单细胞聚类的新方法（scAGC、JojoSCL、scASDC……）几乎都落在
Brief Bioinform / Sci Rep / 生信期刊；能进 CS 一区(ICML/ICLR/NeurIPS)的单细胞论文，
无一例外靠的是**ML/算法/系统层面的新意**，生物数据只是 testbed：
- DRVI（ICLR'25）= 解耦表示学习方法
- scMRDR（NeurIPS'25）= 可扩展生成框架
- "Benchmarking SSL for Single-Cell"（ICML'25 **spotlight**）= benchmark 范式
- "Do LLMs Understand Cell Biology"（NeurIPS'25 D&B）= LLM×细胞的评测范式

**结论：CS 一区的新意载体不能是"聚类精度"，只能是"算法/系统/agent/benchmark"。**
而这恰好和你的 GPU-Agent 毕业论文是同一个方向——所以你的直觉是对的，两者要合起来设计。

## 1. 关键的"缝"：两股热潮之间没人填的空地

我们已经证实，当前有两股 CS 一区级别的热潮正在高速跑：

**热潮 A —— LLM/Agent 自动写 & 优化 GPU 内核**（2025-26 爆发，全是 CS 顶会/CCF-A）：
KernelBench（250 个 PyTorch workload 的标准 benchmark）、AutoKernel、CudaForge
（Coder+Judge+Nsight 反馈）、KernelPro、VibeCodeHPC、PARACODEX（自动并行化+迁移，
ACL'26）、LASSI（OpenMP→CUDA）……见文献表 E 类。

**热潮 B —— 单细胞 GPU 加速**（已成主流生态）：rapids-singlecell（把 scanpy 管线
GPU 化，最高 938×，2026 已进 scverse 核心）、NVIDIA Single-Cell Blueprint。见 D 类。

**中间的缝（没人填）**：
```
rapids-singlecell 只加速了「标准 scanpy 管线」(PCA / neighbors / Leiden / UMAP)。
而这几年爆发的「深度单细胞方法动物园」(scDeepCluster/scDCC/scAGC/JojoSCL/scMAE/
DEC 系/图对比/扩散……几十个) 绝大多数是 CPU-bound、各写各的、没有 GPU-native 实现，
也没有任何 benchmark 或 agent 去系统性地把它们迁移/优化到 GPU。
KernelBench 是通用 PyTorch 算子，不是领域算法；它不覆盖"单细胞算法"这一层。
```

我们自己就撞过这个证据：Phase 2 里 swap-noise 的实现每 batch 拷贝 179MB，GPU 利用率
只有 1-8%（模型小、瓶颈全在 CPU 数据管线）。**深度单细胞方法普遍不是 GPU-native**，
这正是那条缝的活证据。

## 2. 三个候选选题（按"CS一区可行性 × 承上启下贴合度"排序）

### 选题一（★推荐）：单细胞算法的 GPU 迁移 Agent + Benchmark
**一句话**：造一个 benchmark——把 N 个代表性单细胞算法（降维/聚类/上下游）连同
参考实现、正确性判据、数据集打包；再造一个 **LLM-Agent 自动把它们从 CPU 迁移/优化到
GPU**，用"正确性(聚类指标不掉) × 加速比 × 显存"三轴评测。

- **为什么是 CS 一区**：这是 KernelBench 那条线（CCF-A）在**领域算法**上的落地——
  KernelBench 做通用 PyTorch 算子，我们做"单细胞算法"这一垂直层；agent 迁移+正确性
  校验（聚类指标必须不掉）是新问题。可投 NeurIPS D&B / ICML / 系统会 / agent 方向。
- **承上启下**：论文 = benchmark + baseline agent（承上：把我们做过的方法动物园+DEC+
  std-floor 全变成"被迁移对象"和"正确性基准"）；毕业论文 = 把 agent 做强（多 agent、
  硬件反馈、跨算法泛化、自动发现 GPU-native 新实现）（启下）。两者天然连成一条线。
- **我们已有的资产**：一个跑通的方法动物园（scMAE 家族 + DEC + rank13/29 + 图/对比若干）
  + 同管线评测 + 多数据集 + DEC+std-floor 这个稳的正确性锚点。全部变成 benchmark 素材，
  之前的"负结果"在这里**不再是负结果**，而是 substrate。
- **风险**：中。工程量大（要搭 agent + 迁移 harness），但方向明确、热度高、我们有基础。

### 选题二：GPU-native 的单细胞降维/聚类方法（方法论文）
**一句话**：设计一个原生为 GPU 吞吐优化的单细胞表示/聚类算法（比如把对比学习/图割/DEC
重构成 GPU-friendly、大规模可扩展），主打 accuracy-speed-memory 的 Pareto 前沿。

- **为什么可能 CS 一区**：如果新意在"算法为硬件重设计"（不是又一个 loss），且有可扩展性
  故事（百万细胞），可以够 ML/系统会。但**纯精度提升不够**。
- **承上启下**：这个方法本身就是毕业论文 agent 要迁移/优化的"最佳目标之一"。
- **风险**：高。我们已经用 10+ 消融证明"在这个家族里造更好的方法"极难；且方法论文对
  新意要求最苛刻，容易被"这不就是 X+Y"拒。**不建议作为主线，可作为选题一里的一个亮点方法。**

### 选题三：可扩展性/效率轴的单细胞聚类 Benchmark（纯 benchmark 论文）
**一句话**：沿着本仓库同名的 scCluBench，但换一个没人系统做过的轴——**GPU 效率 ×
跨数据集鲁棒性 × 可扩展性**，把方法动物园全评一遍，给出"精度-速度-显存"全景 + 诊断。

- **为什么可能 CS 一区**：NeurIPS D&B / ICML benchmark 赛道认这种（见 SSL-benchmark
  ICML'25 spotlight）。但要有**新洞察**（不只是排行榜），比如我们已有的诊断结论
  （重构≠聚类、伪结构有害、head 非瓶颈、corruption 数据集依赖）。
- **承上启下**：benchmark 直接成为毕业论文 agent 的评测台。
- **风险**：中低。最稳、最快能出，但"天花板"可能不如选题一亮眼。

## 3. 我的推荐：选题一为主，把三/二作为它的两个组成部分

最强的形态是**三合一、但以"GPU迁移Agent+Benchmark"为主叙事**：

```
论文(承上) = "单细胞算法 GPU 迁移与加速的 Agent-Benchmark"
   ├─ 组件1(来自选题三): 方法动物园 + 正确性基准 + 效率全景 + 诊断洞察
   ├─ 组件2(来自选题一): baseline LLM-Agent，自动迁移/优化到 GPU，三轴评测
   └─ 组件3(来自选题二,可选亮点): 一个我们自己重设计的 GPU-native 方法作为 case study

毕业论文(启下) = 把组件2 的 Agent 做成主角
   ├─ 多-agent + 硬件反馈(Nsight) + 迭代优化(照 CudaForge/KernelPro 的范式)
   ├─ 跨算法泛化 + 自动正确性校验(聚类指标不掉是硬约束——这是领域特色，通用kernel没有)
   └─ 面向单细胞的 DSL / 迁移模式库
```

关键卖点（区别于 KernelBench）：**"正确性"在单细胞里不是数值 bit-match，而是"下游
聚类/降维指标不退化"** —— 这是一个通用 GPU-kernel-agent 没有的、领域特有的、更难的
正确性判据。这一点就足以撑起一篇 CS 一区的差异化。

## 4. 上游/下游怎么"增添东西"（回答你的原问题）

你问能否在任务的上游/下游加东西——能，而且选题一天然要求覆盖全链路，因为 agent 要迁移
的正是这一整条：

- **上游**：HVG 选择、归一化、PCA/降维、邻居图构建。rapids-singlecell 已做标准版 →
  我们覆盖"深度降维方法"(DRVI/VAE 系)的 GPU 迁移。
- **核心**：聚类（我们的主场，方法动物园现成）。
- **下游**：轨迹推断、GRN 推断、细胞通讯（文献表 C 类，多为 CPU-bound 深度方法）→
  agent 迁移的高价值目标，且让 benchmark"全链路"而非单点，显著加分。

覆盖全链路 = benchmark 更完整 + 更像"单细胞算法 GPU 化"这件大事，而不是"又一个聚类"。

## 5. 下一步具体行动（低成本、先验证可行性）

不要一上来搭大系统。按"信息量/成本"排：

**Step 1（今天就能做，决定选题一是否成立）：CPU↔GPU 加速缺口实测。**
拿我们方法动物园里 3-5 个代表方法（scMAE/DEC / 一个图对比 / 一个降维），在 CPU 和 GPU
上实测 wall-time + GPU 利用率 + 显存，量化"缝"到底多大。若深度方法普遍 GPU 利用率低、
存在明显可迁移加速空间 → 选题一/毕业论文的前提坐实。（我们 Phase 2 已见 1-8% 利用率，
这一步是系统化确认。）

**Step 2：定 benchmark 的算法清单 + 数据集协议 + 三轴指标。**
算法：从文献表 A/B/C 选 8-12 个有 GitHub 的代表（表里已标 github/venue）。
数据集：动物(Macosko/Quake/Melanoma) + 植物(SRP/CRA) + 大规模(百万级，测可扩展性)。
指标：正确性(ARI/NMI/label-free) × 加速比 × 峰值显存 × 迁移成功率。

**Step 3：baseline 迁移 Agent 原型。**
照 CudaForge/KernelPro 范式：Coder + Judge + 硬件反馈(Nsight/torch profiler) + 
"聚类指标不掉"的正确性 gate。先在 1-2 个方法上打通闭环。

**Step 4（并行）：把已有诊断洞察写成 benchmark 的"分析章"。**
重构≠聚类、伪结构有害、head 非瓶颈、DEC+std-floor 机制、corruption 数据集依赖——
这些都是现成的、别的 benchmark 没有的洞察，直接进论文。

## 6. 风险与备选

- 若"迁移 Agent"工程量超预算 → 退到选题三（纯 GPU-效率 benchmark + 诊断洞察），仍可投
  NeurIPS D&B，且毕业论文再补 agent。
- 若想要更"方法味" → 在选题一里嵌入选题二的 GPU-native case-study 方法作为亮点。
- FM 路线（scGPT/植物 scAraFM）**不作为主线**：文献证明 FM zero-shot 聚类常被简单方法
  打败(Genome Biol'25)，且算力/依赖重、新意难立。可作为 benchmark 里的一个被评测对象。
